# Notion自動記録の設定と確認

Chrome拡張が取得した解答を、各Macの収集プログラムから同じNotionへ送ります。
各Macで解いた同じ問題も、解答ごとに別の行になります。
この実装は接続設定後、収集プログラムが起動している間に動作します。
ログイン時の自動起動は、利用者が希望したMacに個別に設定します。

## 導入前に用意するもの

Notionの内部接続（自分のプログラムがNotionへアクセスするための接続）を作り、次の権限を付けます。

- コンテンツの読み取り
- コンテンツの挿入
- コンテンツの更新（問題との関連付け修復に使用）

対象は既存の「QB解答ログ」と「QB問題マスター」です。
両方をその接続と共有してください。ユーザー情報、メール、コメントの権限は不要です。
接続用シークレットはチャットに貼りません。下記の設定プログラムへ非表示入力します。

「QB解答ログ」には既存の列に加え、テキスト型の `記録データV1` が必要です。
これは取得した解答事実の原本で、問題文や解説は含みません。
プログラムは保存先の構造を読み取り、不一致の場合は記録を追加せず停止します。

Notionの「解答日時」「取得日時」は、一覧表示用に分単位で保存します。
実接続で秒以下が切り落とされることを確認したためです。
秒以下を含む正確な日時は「記録データV1」に保持し、同期時には元の解答データと完全一致することを確認します。
日時欄の照合は、元の日時そのものか、その日時の秒以下だけを切り落とした値に限定します。
同じ分に解いた別の解答は、異なるイベントIDとしてそれぞれ保存します。

## このMacに設定する

完成版のプロジェクトフォルダを使用します。初期版のDeveloperフォルダでは動きません。
Node.js 24.19以上25未満と、固定した依存関係を使い、検証済みのbuildを用意してください。

プロジェクト直下で次の形式を使用します。2つのIDはNotion仕様のdata_source_idです。
database_idやページIDと取り違えないでください。

```sh
pnpm --filter @qb-study/history-collector notion:configure 解答ログのdata_source_id 問題マスターのdata_source_id
```

設定プログラムは接続用シークレットを非表示で受け取り、指定先の構造を実際に読んで確認します。
この操作で学習記録は追加しません。
成功すると、本人だけ読める設定ファイルとシークレットファイルを次の場所に作ります。

```text
~/Library/Application Support/qb-study-system/notion-sync.json
~/Library/Application Support/qb-study-system/notion-token
```

既存の設定やシークレットがある場合は上書きせず `NOTION_SETUP_EXISTS` で止まります。
設定のJSONには接続先IDとシークレットファイルの場所を保存します。シークレット本体は別ファイルです。
設定を別Macにコピーする場合も、端末ごとのSQLiteを複製または共有してはいけません。

設定後に収集プログラムを起動します。

```sh
pnpm --filter @qb-study/history-collector start
```

通常のローカル保存に加えて、15秒ごとに新しい記録を同期します。
初回起動より前の学習記録は対象外です。過去の検証データを自動でNotionへ送らないためです。
一度対象になった記録は、再起動しても送信待ちに残ります。

## Macへのログイン時に自動起動する

macOSのLaunchAgent（利用者のログインに合わせてプログラムを起動する設定）を使用します。
自動起動は設定したMacと利用者にだけ有効で、別Macには引き継がれません。
ChromeやCodexを開く前でも収集プログラムを起動できますが、解答の取得にはChromeのQB記録拡張が必要です。

実行用のNode.js、収集プログラムをまとめた単一ファイル、SQLiteの形式定義を、次の場所へ実体コピーします。
開発用フォルダやCodexのキャッシュは、自動起動の参照先にしません。

```text
~/Library/Application Support/qb-study-system/runtime/node-v24.19.0/bin/node
~/Library/Application Support/qb-study-system/runtime/collector/dist/collector.mjs
~/Library/Application Support/qb-study-system/runtime/collector/migrations/
~/Library/LaunchAgents/local.qb-study.history-collector.plist
```

起動設定には、上記の実行ファイル、既存SQLite、Notion設定、ログの絶対パスを指定します。
接続キー自体は起動設定へ書きません。
ログイン時に起動し、異常終了した場合は30秒以上の間隔を設けて再起動します。
正常終了した場合は自動で再起動しません。
ログは `~/Library/Application Support/qb-study-system/logs/` に保存します。

導入時は既存の収集プログラムだけを正常終了させ、同じSQLiteとNotion設定を使うLaunchAgentへ切り替えます。
設定の読み込み、単一起動、保存済み履歴の保持を確認します。
実際のログアウト・再ログインを行っていない場合は、その検証は未実施と記録します。
収集プログラムの更新時には、検証後に上記の配置先も更新する必要があります。
開発用フォルダのコード変更だけでは、稼働中の版は変わりません。

自動起動を解除する場合は、このLaunchAgentを登録解除し、対応するplistだけをLaunchAgentsの外へ移します。
SQLiteとNotion設定はそのまま残します。

## 動作を確かめる

利用者が通常どおりQBで記録開始に同意して問題を解き、Notionの解答ログを開きます。
問題番号、日時、選択記号、正誤が一致し、問題マスターに関連付いていることを確認します。
次に別Macでも別の解答を行い、両方の行と合計回数を確認します。
この実地確認をしていないMacは「接続確認済み」と扱いません。

拡張のOutboxが0でも、それはMac内への保存完了です。
Notionへの保存完了は収集プログラムの `confirmed`、送信待ちは `pending`、確認が必要な状態は `blocked` に表示されます。
いずれもその回の確認件数またはローカルの送信状態であり、Notionの全Mac総件数とは異なります。

## 通信失敗と停止

一時的な読み取り失敗や明確な送信制限は待機して再試行します。
Notionへの新規作成中に通信が切れた場合は、同じイベントが保存済みかを照合します。
照合できない場合は重複作成を避けて保留します。元のデータはMac内に残ります。
履歴が保存済みか不明な状態でSQLiteの同期記録を消したり、イベントIDを書き換えたりしないでください。

主な停止コード:

| コード | 状態と対処 |
|---|---|
| NOTION_SCHEMA_MISMATCH | 列の型や関連先が異なる。対象のNotion構造を確認する。 |
| NOTION_UNAUTHORIZED / NOTION_FORBIDDEN | 認証または対象ページへの権限を確認する。 |
| NOTION_CREATE_UNCONFIRMED | 作成成否が不明。NotionのイベントIDと原本を照合する。 |
| NOTION_DUPLICATE_EVENT / NOTION_EVENT_CONFLICT | 重複または内容不一致。勝手に削除せず、元の記録を比較する。 |
| NOTION_REMOTE_MISSING | 一度確認したNotion行が見えない。削除や権限変更を確認する。 |

停止する場合は収集プログラムを終了します。
ローカル記録だけ続ける場合は設定ファイルの `enabled` を `false` にして再起動します。
同期記録と解答は削除されません。元に戻すには `true` にして再起動します。

新しいSQLite形式を古いプログラムで開くと拒否されます。
コードを古い版へ戻すより、同じ版で同期を無効化する方法を使用してください。
本番のDB更新前にはバックアップを別のローカルファイルとして保存してください。

## 既存の取得制限

同じ画面で直ちに同じ問題を解き直す操作は、拡張が表示の再描画と区別できない場合があります。
この操作の新たな実地確認と取得側の修正は未実施です。
別の解答イベントとして取得できた記録は、同じ問題でもすべて別の履歴として送信します。
背景処理への保存前にタブが閉じた記録や、未対応の画面構造で取得できなかった記録を後から推測で補いません。
