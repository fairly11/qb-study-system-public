# 日次復習の実行手順

Notionに届いた解答履歴から復習候補を計算し、QBの問題セットへ登録する手順です。
計算とNotionへの計画保存はコマンドで行い、QBへの登録はブラウザで操作します。
コマンド自体にブラウザ操作や定時実行の機能はありません。

## 実行環境と設定

[Notion同期](NOTION_SYNC.md) を設定し、リポジトリ直下で `pnpm build` を実行しておきます。
同じ計画の二重作成を避けるため、復習処理を担当するMacは一台に固定します。

設定は `~/Library/Application Support/qb-study-system/review-config.json` です。
所有者だけが読み書きできる権限（`0600`）で保存します。

| 項目 | 値 |
|---|---|
| `schema_version` | `"1"` |
| `publisher_host` | 実行するMacのホスト名。Node.jsの `os.hostname()` と一致する値 |
| `notion_parent_page_id` | 復習計画を保存するNotion親ページのID |
| `max_questions` | 一日の問題数上限。1〜100 |
| `request_retention` | 任意。目標想起率。省略時は0.9 |
| `per_question_daily_cap` | 任意。同じ問題の一日あたりの上限。省略時は2 |
| `settings_version` | 任意。設定の識別名 |

日次計画と操作記録は、同じ保存先の `daily-review/YYYY-MM-DD/` に作成します。
収集用のNotion接続には、復習計画の親ページへのアクセス権も必要です。
初回の列設定には `configure-schema` を使います。この操作はNotionの学習区分用の列を追加します。

## コマンド

リポジトリ直下で実行します。

```sh
pnpm --filter @qb-study/history-collector review サブコマンド 引数 対象日
```

対象日は `YYYY-MM-DD` で指定します。
引数のないコマンドに対象日を指定する場合は、引数を `""` にします。
日付を省略すると、日本時間の午前4時を日付の区切りにした当日を使います。

| サブコマンド | 引数 | 処理 |
|---|---|---|
| `preview` | なし | 現在の履歴から候補を表示する。日次計画は保存しない |
| `configure-schema` | なし | Notionの学習区分用の列を設定する |
| `prepare` | なし | 候補を固定し、ローカルとNotionに計画を保存する |
| `begin-set` | なし | QBセットの作成予定を記録し、作成可否を返す |
| `record-set` | QBセットのURL | 作成したセットのURLを保存する |
| `remaining` | 問題番号配列のJSONファイル | 登録済みの並びを確認し、不足分を返す |
| `verify-set` | 問題番号配列のJSONファイル | 全件の番号と順序を照合する |
| `link-set` | なし | 照合済みのセットリンクをNotionへ保存する |
| `status` | なし | 保存済み計画と、Notionへ届いた解答から進捗を表示する |
| `amend-day` | なし。対象日必須 | 当日計画へ明示的に追加する候補を保存する |

配備済みの単一ファイル版では、Node.js、`review.mjs`、サブコマンドの順で呼び出します。
引数と対象日の順序は同じです。

## 復習候補の選び方

- 対象は第116回〜第120回の国試問題です。年が変わっても自動では移動しません。
- 最大100問まで、設定の `max_questions` を上限に選びます。候補が少なくても範囲外や期限前の問題で補充しません。
- 手動期日、直近の不正解、通常候補、同日再試行の優先分類と、科目・分野の配分を使います。
- 同じ優先分類と科目・分野の配分条件では、忘却リスク（1−予測想起率）を第120回だけ1.25倍にして比較します。同値なら第120回を先にし、その後は期日と問題番号の順に並べます。
- 予測想起率が不明なら推測で補わず、比較上のリスクを0として扱います。
- 対象日の翌朝4時より前に期限を迎える問題を含めます。たとえば11月20日分には、11月21日4時未満の期限を含み、4時ちょうどは次の日へ回します。

期限の境界は計画の `due_before`、計算に使った履歴の締め切りは `as_of` に保存します。
実行時刻が遅れても、期限を実行時点から24時間後へずらしません。
範囲外の解答も学習履歴として保持し、候補から外した理由を記録します。

同日の計画は初回に固定します。
再実行や、その後の解答によって候補を入れ替えません。
古い版で保存した計画も、保存時の順序と計算方式を維持します。

## 一日の計画を作る

1. `prepare` を実行します。既存の当日計画があれば再利用します。
2. 問題数が0なら、Notionの候補なしページを結果とし、QBに空セットは作りません。
3. QBへログインし、問題セット一覧を開けることを確認します。
4. `begin-set` を実行し、セット名と問題番号の一覧（manifest）を取得します。
5. `existing` があれば、そのURLのセットを使います。
6. `may_create` が `false` でURLが不明なら、QBの一覧から `manifest.name` と完全一致するセットを探します。一件だけ見つかった場合にURLを保存し、0件または複数件なら調査します。
7. `may_create` が `true` の場合だけ、新しいセットを一つ作ります。作成直後に `record-set` でURLを保存します。
8. 次節の手順で問題を登録し、`verify-set` で全件を照合します。
9. `link-set` でNotionにセットリンクを保存します。

履歴の取得に失敗した場合は処理を止め、古い履歴で代わりの計画を作らないでください。
ログインの途中では `begin-set` を実行しません。作成予定が記録されるためです。
再開時は保存済みの当日計画とセットURLを使います。

## QBへ登録して照合する

QBの問題セット一覧で「＋」から「問題セット追加」を選び、manifestの名前で保存します。
作成の応答が不明な場合は、一覧を読み直して既存セットを探してください。
同名セットを繰り返し作ると、どれが計画に対応するか分からなくなります。

1. `manifest.question_ids` の順に問題番号を検索します。
2. 番号の完全一致を確認し、「問題セットへ追加」で対象セットを選びます。
3. 「OK」で確定し、次の問題に進む前に保存先の件数が増えたことを確認します。
4. 最初の5問（5問未満なら全問）で、対象セットを「追加日が古い順」にして番号と順序を確認します。
5. 残りを登録した後、ページを再読み込みし、全ページの問題番号を表示順に読み取ります。
6. 番号配列をJSONファイルに保存し、`verify-set` へ渡します。

番号配列の形式例:

```json
["119A12", "120B3"]
```

不足、余分な問題、重複、順序の違いがあれば照合は成功しません。
登録途中で止まった場合は、実際のセットを読み直し、`remaining` で保存済みの先頭部分と不足分を確認します。
予定の先頭から連続した並びでない場合は、追加を進めず原因を調べてください。
問題文や解説の取得、試験的な解答は不要です。

## 当日セットへの追加

旧方式で固定した当日計画へ、翌朝4時より前に期限を迎える問題を追加する機能です。
通常の日次実行には組み込まず、当日セットに追加する場合だけ `amend-day` を使います。
元のセットとNotionリンクの照合が完了していることが前提です。

1. 元のセットを「追加日が古い順」で読み直し、保存済み計画と一致することを確認します。
2. `amend-day "" YYYY-MM-DD` を実行します。保存済みの予測から、従来は `not_due` だった候補を残り枠に選びます。
3. 返されたmanifestを使い、元の問題を先頭に残したまま不足分だけを同じセットへ追加します。
4. 全件を読み直して `verify-set` を実行し、`link-set` でNotionの追記も照合します。

`REVIEW_DAY_AMENDED` はローカルへの追加計画の保存完了です。
QBとNotionへの反映は、その後の操作で行います。
元の計画は残し、追加内容を別の記録として保存します。
途中で止まった場合も同じ追加計画を再利用し、作成予定を消してやり直さないでください。

## 演習と進捗

セットのリンクから演習を始めると、拡張が確認済みの復習セットとして記録します。
問題への直接移動は原則「通常学習」です。
区分を変える場合は拡張の「通常学習」「復習課題」を選びます。
変更はその演習の以後の解答へ適用されます。

`status` はNotionへ届いた実解答を照合します。
不正解も実施数には含めますが、習得済みとは扱いません。
解答した回数と、解答した問題の種類数は別に数えます。
通常学習として解いた記録は記憶予測に使いますが、復習の実施数には含めません。

## 障害からの復旧

`REVIEW_PUBLISHER_LOCKED` は、別の実行が処理中か、終了した実行のロックが残っている状態です。
`owner.json` のプロセスIDを確認し、動作中なら終了を待ちます。
そのプロセスが存在しないことを確認できた場合だけ、ロック用の `owner.json` と空の `publisher.lock` フォルダを除去します。
計画、manifest、作成予定、照合結果は削除しません。

チェックサムが一致しない場合は、保存記録の変更や破損を調べてください。
Notionの作成結果が不明な場合は、同日ページを読み戻して照合します。
見つからないことだけを理由に再作成しません。
同日で内容の異なるページがある場合は、自動処理を止めて比較します。
