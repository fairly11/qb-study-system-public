# QB日次復習の実行手順

## 保存場所

実行担当: review-config.jsonに記載した1台のみ。
標準の保存先: ~/Library/Application Support/qb-study-system。
秘密の接続キーを表示・転記しない。
日次計画と操作記録: daily-review/YYYY-MM-DD。
本番実行プログラム: runtime/collector/dist/review.mjs。
Node: runtime/node-v24.19.0/bin/node。

呼び出しはNodeの絶対パス、review.mjsの絶対パス、サブコマンドの順。
prepare / begin-set / record-set URL / remaining IDs_JSON_FILE / verify-set IDs_JSON_FILE / link-set / status。
特定日は `review.mjs サブコマンド argument YYYY-MM-DD` の順で指定する（argumentが不要な場合は空文字列）。
`amend-day` は下記の明示的な追記だけに使い、通常の日次実行には組み込まない。
previewは読み取りのみで、その日の計画を保存しない。
configure-schemaは初回移行時だけ実行する。

## 午前4時の実行

1. 実行ホストを確認する。設定と違うMacでは公開しない。
2. prepareを実行する。Notionから履歴と手動設定を取得し、第116回〜第120回の国試問題から最大100問の固定候補と理由を保存する。
3. 失敗時はエラーコードを報告する。履歴取得に失敗したとき、古いデータで代替生成しない。
4. 同日計画がすでにあるときは再計算しない。
5. 問題数0ならQB空セットを作らず、候補なしのNotionページを結果とする。
6. 下記のログイン復帰確認を先に行い、QBの問題セット一覧を操作できることを確認してからbegin-setを実行してmanifestを得る。
7. existingがあれば、そのURLのセットを確認する。新規作成しない。
8. may_createがfalseでexistingがないときは、QBの問題セット一覧でmanifest.nameと完全一致するセットを探す。1件ならURLを記録し、0件または複数件なら停止する。書込の応答が不明な状態で再作成しない。
9. may_createがtrueのときだけ、その名前で新規セットを1つ作成する。返ったセットURLをrecord-setで保存する。
10. 次のUI手順で問題を登録する。
11. 全件照合後verify-setを実行する。成功後にlink-setでNotionのセットリンクを保存する。
12. 生成したセットURLとNotion候補ページを結果として通知する。すでに完成していて変更がない場合は通知しない。失敗や利用者操作が必要な場合だけ理由を通知する。

2026年10月30日から、選択器の版4で新しく生成する復習計画は、第116回〜第120回（両端を含む5回分）の国試問題だけを候補にする。
第115回以前と第121回以降は、手動の復習日が到来していても、直近の不正解や復元履歴があっても候補から除外する。
これは固定範囲であり、年が変わっても自動ではずらさない。
対象範囲内で従来の優先順位を適用し、最大100問を選ぶ。対象問題が少なくても範囲外の問題では補充しない。
範囲外の解答履歴、記憶状態と学習集計は保持し、除外理由 `outside_exam_scope` を計画へ記録する。
すでに保存済みの日次計画や作成済みセットは変更せず、同日の再実行では保存済み計画を再利用する。
旧計画の照合と明示的な追記の再現処理も従来どおり維持する。

版3から引き続き、その対象日の翌朝04:00 JSTより前にモデル上の復習期限を迎える問題も朝の候補に含める。
たとえば10月21日分は10月22日03:59:59.999までを対象とし、10月22日04:00ちょうどは次の日に回す。
この期限境界は計画の `due_before` に保存する。
入力する解答履歴と記憶予測は実際の計算時刻 `as_of` までに限り、午後に解く予定の解答を取り込まない。
実行が遅れても期限境界を24時間後へずらさず、対象日の翌朝04:00に固定する。
停止、今日の正解、同一問題の回数上限、未来の手動復習日による除外は維持する。
候補が100問未満でも埋めない。作成後に履歴が増えても当日候補を自動で入れ替えない。


2026年11月11日の仕様変更以降、新規計画は選択器の版5を使う。
手動期日、直近不正解、通常候補、同日再試行の優先分類と、科目・分野の配分は維持する。
その条件が同じ候補では、忘却リスク（1−モデルの予測想起率）を第120回だけ1.25倍にして、高い順に選ぶ。
同じ補正値なら第120回を先にし、その後は従来のモデル期日と問題番号の順とする。
予測想起率が不明な場合は数値を作らず、従来どおり比較上のリスクを0とし、同順位のときだけ第120回を優先する。
記憶予測、復習期限、候補の除外条件、116〜120回の固定範囲、上限100問は変えない。
50%などの回別固定枠は設けず、期限前の問題で補充しない。候補が100問以下なら主に並び順、上限を超える場合は選抜にも影響する。
選定理由には `exam_priority_weight` と補正係数を保存し、Notionにも表示する。
本日分を含む保存済み計画とセット、旧計画への明示的追記は、元の順序と計算方式を保持する。

## QBの画面操作

内蔵ブラウザを使う。現時点の画面を見て操作先を確認する。
対象外の既存問題セットや学習記録は変更しない。
完成済みの対象セットへの追記は、下記の手順について利用者の明示的な依頼がある場合に限る。
問題文、選択肢本文、解説、画像は収集・保存・ログ出力しない。
DOMの全テキストを取得せず、問題番号、ボタン、件数、セット名だけを調べる。

### ログイン表示になった場合

QBトップが未ログイン表示でも、その表示だけで停止しない。
最初に公式QBトップの「ログイン」を1回押し、既存の認証状態で復帰できるか確認する。
ID・パスワードの入力画面へ進んだ場合も、その表示だけで停止しない。
保存済みログインの利用は、そのアカウントの利用者が対象サイトと操作を許可している場合に限る。
ブラウザが正式に提供する自動入力機能を使い、秘密の値を読み出さない。
現在のログイン画面でアカウント欄またはパスワード欄をクリックする。対象アカウントとパスワードが既に自動入力されていれば、候補メニューの表示・選択は不要で、次の入力状態の確認へ進む。まだ自動入力されていない場合だけ、対象サイトと利用中のアカウントに一致する保存済み候補を一つ選ぶ。複数候補の先頭を無条件に選ばない。
対象アカウントの入力済み状態と、伏せ字のパスワード欄が埋まっていることを画面で確認してから、ログインフォームを1回送信する。
自動入力されず候補も出ない場合は、画面上で別の該当入力欄を確認できるときだけ、その欄でも候補を確認する。候補が出ないまま同じクリックや失敗したログイン送信を繰り返さない。
パスワードを表示・抽出・コピー・手入力しない。保存済みパスワードの管理画面や保存ファイルから値を取り出さず、ID・パスワード・Cookie等の認証情報を作業ファイルやログへ転記しない。
自動入力やログイン送信だけを復帰成功とせず、利用中のQB（医師国家試験）の問題セット一覧を公開画面から読み取れることを確認する。
追加認証、CAPTCHA、新しい権限への承認、対象アカウントの特定、自動入力も保存候補の選択もできない状態（候補が表示されない、操作範囲外、操作拒否など）で利用者にしかできない操作が残る場合、別アカウント・別製品に移動した場合、またはログインが失敗した場合は停止する。原因と実施済み対処を記録し、必要な操作だけ知らせる。
操作拒否を別のアプリ名・ツール・保存ファイルの読み取りで迂回しない。
ログイン復帰確認はbegin-setより前に行う。begin-setはセット作成意図を保存するため、ログイン待ちの段階では実行しない。
復帰後は保存済みの同日日次計画、manifest、公開意図、結果から再開する。候補の再計算、作成意図の削除、応答不明なセットの再作成は行わない。

### 問題セットの作成と照合

問題セット一覧の青い大きな「＋」を押して追加メニューを展開し、「問題セット追加」からmanifest.nameを入力して保存する。
展開前はメニュー内の子ボタンが無効（disabled）になっているため、その状態だけで容量制限と判断しない。
問題検索でmanifest.question_idsの順に1問ずつ検索する。
検索結果の問題番号が完全一致したことを確かめ、「問題セットへ追加」を開く。
保存先のセット名と件数を確認して選び、必ず「OK」で確定する。
Escapeで閉じた場合は保存済みと扱わない。
「OK」の直後に続けて遷移すると、保存がまだ反映されていない場合がある。
次の追加前に、保存先の表示件数が直前の「OK」で確定した分を含む件数と一致するか確認する。
未反映または不一致なら追加を進めず、既存セットを再読込して問題番号を追加日の古い順に読み戻し、remainingで保存済みの並びと未登録分を確認してから再開する。
複数番号検索を使う場合はORとするが、追加順保持のため登録は1問ずつ行う。

既存セットの復旧では、追加日の古い順で番号を読み戻す。
remainingへ番号配列JSONを渡す。
予定の先頭から連続した並びでなければ停止する。

最初の5問（候補が少ない場合は全問）で保存先と順序を確認する。
問題セット画面の「追加日が新しい順」を切り替え「追加日が古い順」にする。
残りを追加したらページを再読込し、全問題番号を表示順に読み戻す。
画面が複数ページなら全ページを確認する。
候補と別に追加された連問、欠落、重複、順序をverify-setで検査する。
相違があれば完成と報告しない。勝手に問題を削除しない。
試験的な解答や演習開始ボタンの操作は不要。

## 利用者が依頼した当日セットへの追記

旧方式で作成した当日セットへ、翌朝04:00より前に期限を迎える問題を追加する場合の手順。
利用者が当日分への追記を明示的に依頼した場合だけ実行する。
過去の日付を順に処理したり、通常の `prepare` から自動で追記したりしない。
新規の追記計画は、その時点の最新04:00が属する日だけ作成できる。
元のQBセット、全件照合、Notionページとセットリンクが確認済みであることが前提となる。

1. 対象日の保存済み計画と、同じURLのQBセットを確認する。追加日の古い順で元の問題番号と順序が一致していることを確認する。
2. `amend-day "" YYYY-MM-DD` を実行する。保存済みの予測から、従来 `not_due` だった問題のうち新しい期限範囲に入るものだけを残枠に選ぶ。新しい履歴では再計算しない。
3. 返された有効manifest（追記後の全問題一覧）を使う。元の問題と順序は先頭に保持され、その後ろに追加候補が続く。別のセットは作らない。
4. 現在の全問題番号を `remaining` へ渡し、返された不足分を既存セットへ順に追加する。先頭から連続した並びでない場合は停止する。
5. セットを再読込し、全ページの全問題番号を古い順に読み戻して `verify-set IDs_JSON_FILE YYYY-MM-DD` へ渡す。追記後の照合結果は `qb-verified-revision-1` に保存される。
6. `link-set "" YYYY-MM-DD` を実行する。既存Notionページの元の計画とリンクを保持し、同じセットURLに結び付く追記内容を別の節として追加する。
7. QBの追記後照合とNotionの追記後照合の両方が完了したことを確認してから完了を報告する。片方だけなら追記途中として扱う。

10月21日分への明示的な追記をローカルに記録するコマンド例（作業フォルダは任意）：

```sh
"$HOME/Library/Application Support/qb-study-system/runtime/node-v24.19.0/bin/node" \
  "$HOME/Library/Application Support/qb-study-system/runtime/collector/dist/review.mjs" \
  amend-day "" 2026-10-21
```

成功時は `REVIEW_DAY_AMENDED` と追記後のmanifestを返す。この段階ではQBとNotionの追記は未完了である。
元の `plan` と `manifest` は上書きせず、`revision-1` と `manifest-revision-1` を追記する。
たとえば元が4問なら、その4問の内容と順序を維持し、追加分は5番目以降になる。
`remaining`、`verify-set`、`status` は追記後の有効manifestを参照する。

途中で停止した場合は保存済みrevisionと実際のQB一覧を照合して再開する。
Notion追記の応答が不明な場合、既存の追記内容を読み戻して照合する。
見つからないことだけを理由に追記を繰り返したり、操作意図を削除したりしない。
通常の `prepare` を再実行しても、別の追記計画は作られない。

## 利用者の学習

QBの問題セットを開いて演習を始めると、拡張が自動で記録する。
目的の選択や「記録を開始」は不要。
確認済みのシステム復習セットからの演習を復習とし、それ以外は原則通常学習にする。利用者が現在の演習を「復習課題」と選んだ場合も復習として保存する。
セット名や問題の一致だけで復習扱いにしない。
問題画面へ直接入ると移動元セットを判定できないため、原則通常学習になる。復習時はセットのリンクから入るか、拡張で「復習課題」を選ぶ。
セット照合の通信失敗や不正なセットIDでは、解答を記録しながら「判定未確認」と表示する。
「通常学習」「復習課題」ボタンで現在の演習の区分を選べる。選択は以後の解答に適用し、既存の解答や送信待ち記録は変更しない。
手動選択で計画IDを推測しない。計画IDなしの復習は、既存の進捗集計条件（計画内の問題番号と時刻）を満たした場合に計上する。
一時停止と再開は拡張の画面から行う。次の演習では再び自動開始する。
従来の未分類記録はそのまま残る。
セット内の問題を通常学習として解いた場合も、記憶予測には反映されるが復習の実施数には含まれない。

進捗はstatusでNotionへ届いた実解答を照合する。
1、3、5番だけ解いた場合はその3問だけを実施済みとする。
不正解も実施数には含めるが習得済みにしない。
解き直しの回数と実施した問題の種類数を別に表示する。
候補は当日自動で追加補充しない。上記の明示的な追記は、保存済み計画を残した別記録として扱う。

## 障害と復旧

REVIEW_PUBLISHER_LOCKEDは実行中または終了したプロセスのロックが残っている状態。
owner.jsonのPIDを確認し、実行中なら終了を待つ。
プロセスが存在しないことを確認してから、ロック用owner.jsonと空のpublisher.lockディレクトリだけを除去する。
日次のplan、manifest、公開意図、結果のファイルは削除しない。
照合用ファイルのchecksumが一致しない場合は停止する。

Notion作成結果が不明なときは同日ページの照合だけを行う。
見つからないことだけを根拠に再作成しない。
Notionに同日別内容の候補があれば手動確認を求める。

Chromeの既存拡張は同じフォルダで更新する。
拡張を削除して入れ直すと送信待ちや識別情報を失うおそれがあるため、更新後は既存拡張の再読み込みを使う。
Macの再起動は不要。
