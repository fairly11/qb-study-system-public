# ADR-0018: 観測から確認した解答の補完

- 状態: 採用
- 決定日: 2026-10-19
- 関連: ADR-0004, ADR-0006, ADR-0014, ADR-0015

## 背景

自動記録で欠けた解答を、確認済みの観測から補完する場合を扱う。
問題番号、解いた日、正誤は確認できるが、選択番号と正確な解答時刻は確認できない。
観測した瞬間を解答した瞬間として保存すると、既存の直接取得データと精度の異なる証拠が混ざる。

## 保存する証拠

既存の `AttemptEventV1` と `HistorySnapshotV1` を変更せず、独立した `RecoveredAttemptV1` を追加する。
これは確認済みの解答1回を表し、履歴画面の最終状態だけから解答回数を推測して作成しない。

- `recovery_id`: 補完作業で固定するUUID。同じ補完を再実行するときも変更しない。
- `question_key`, `answered_on`, `result`: 確認できた問題番号、東京の暦日、正誤。
- `observed_at`: Computer History が証拠を観測した瞬間。
- `recovered_at`: 補完作業で原本を確定した瞬間。
- `selected_option_indices: null`, `study_mode: unclassified`: 選択番号と目的は推測しない。
- `source_system`, `source_event_id`, `source_segment`: 証拠の種類と識別子。問題文や画面本文を含めない。

`answered_at` は持たない。
日付の入力から架空の時刻を作らず、観測時刻より後の日付、補完時刻より後の観測、未知の追加属性を拒否する。
この新形式は既存のV1レコード集合に混ぜず、別の型、検証関数、JSON Schemaを公開する。

## Notionでの保持と作成

ADR-0014に従い、複数Macで共有する原本は既存の解答ログに置く。
`補完データV1` に新形式の全項目、`補完ID` に固定UUID、`観測日時` に観測時刻の表示を追加する。
`記録元` は `Computer History補完`、`学習種別` は `未分類` とする。
既存の `記録データV1`、`イベントID`、`自分の解答` は空欄、`解答日時` と `学習日` は日付だけにする。
Notionの日付属性で失われる秒の精度は、補完原本内の観測時刻と補完時刻で保持する。

スキーマ追加は `ensureRecoveredAttemptSchema()` の明示呼出しだけで行う。
通常の取得・同期や読み込みではスキーマを変えず、既存の選択肢と列を保持する。
新しい列のない旧構成は、従来どおり読み込める。
補完のためにSQLiteの直接取得テーブルへ架空の解答を挿入しないため、既存SQLiteスキーマの変更は不要とする。

作成前に固定IDを検索し、同じIDの同じ内容なら既存の行を返す。
別内容、複数の行、同日同問の既存解答、判別できない既存行がある場合は作成を止める。
問題マスターは問題キーだけから作成でき、架空の `AttemptEventV1` は必要としない。
作成処理は1回だけ送信し、応答が不明な場合は `ambiguous` を返す。
呼出し側は作成前の意図と返されたページIDを永続化し、不明な応答の後に新しいIDや再作成を行わない。
Notionには原子的な一意制約がないため、別端末から同時に行う補完作成の重複を完全には防げない。
同じ補完記録を書き込む処理は一つに限定する。

## 読み込みと復習への反映

全ページを読み、新しい原本と表示列の一致を検証した補完だけを `recoveredAttempts` に返す。
同じ補完IDで同じ内容の行は一度だけ数え、内容の競合は停止する。
別IDでも同じ日・同じ問題の補完が複数ある場合は、別の解答であると立証できないため停止する。
観測時刻・補完時刻・解答日が集計時点より未来にある補完は、その集計から除外する。

同じ日・同じ問題の直接取得が後から届いた場合、補完は原本を残したまま集計から抑制する。
直接取得の解答時刻と取得時刻の両方が集計時点以前の場合だけ、この抑制を適用する。
実際には同日に別の解答だった可能性があっても、二重計上を避ける方を選ぶ。
`集計除外` の行は従来どおり対象外とする。

補完は未分類の解答数と問題の復習優先度に反映できるが、正確な瞬間を必要とするFSRSへは渡さない。
補完を使う復習時期は日付単位の規則として説明し、直接取得による記憶モデルの予測と区別する。
すでに確定した日次計画と公開したQBセットは変更しない。

## 検証

契約では、余分な本文、架空の解答時刻、選択番号、目的、前後関係の矛盾を拒否する。
Notionのテストでは、旧構成の読込、完全なページ分割取得、原本と表示列の不一致、同一IDの再利用、同日同問の重複防止、後着の直接取得による抑制、未来の証拠の除外、通信応答が不明なときの再作成防止を確認する。
通信は模擬応答を使い、実データへの追加と分離してテストする。
